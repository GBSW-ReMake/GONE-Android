# GONE Android 개발 워크플로우

기능 하나는 계획서부터 개발자 머지까지 아래 11단계를 순서대로 진행합니다.

```text
계획서 작성 → 계획서 검토 → GitHub 이슈 → 브랜치 분기 → 기능 개발
→ QA 및 이슈 보고 → 수정 → 최종 보고 및 검토 → 최종 커밋·Push → PR → 개발자 머지
```

## 절차

1. `doc/fe/plans/`에 목적, 사용자 시나리오, 화면 상태, API 의존성, 완료 기준을 기록합니다.
2. 개발자가 계획서를 승인합니다. 승인 전에는 이슈, 브랜치, 구현을 시작하지 않습니다.
3. GitHub 이슈에 계획 요약과 완료 기준을 작성합니다.
4. `dev`에서 `feat/<이슈번호>-<기능명>` 또는 `fix/<이슈번호>-<설명>` 브랜치를 만듭니다.
5. View는 UI와 이벤트 전달에만 집중합니다. 상태와 화면 로직은 Controller 또는 Notifier에 둡니다.
6. 정상, 로딩, 빈 상태, 오류, 권한 거부 상태를 QA하고 결과를 `doc/fe/issues/`에 기록합니다.
7. Major 이상 이슈는 개발자와 수정 방향을 합의한 뒤 고칩니다.
8. 구현 내용, QA 결과, 제한사항을 `doc/fe/reports/`에 기록하고 개발자 검토를 받습니다.
9. 논리적 변경 단위로 커밋하고 기능 브랜치를 Push합니다.
10. `dev`를 대상으로 Ready for review PR을 만듭니다.
11. 개발자가 코드 리뷰와 QA 결과를 확인한 뒤 직접 머지합니다.

## 검증 명령

```bash
flutter analyze
flutter test
flutter build apk --debug
```

- Android Studio Emulator 또는 실기기에서 핵심 사용자 흐름을 확인합니다.
- 빌드 도구 또는 SDK 문제로 검증하지 못한 항목은 QA 보고서에 원인과 재검증 방법을 기록합니다.
